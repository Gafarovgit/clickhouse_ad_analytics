# Архитектурный отчёт: рекламная аналитика в ClickHouse

## 1. Цель и модель данных

Решение предназначено для анализа эффективности рекламных кампаний. Модель включает два справочника (`channels`, `campaigns`), слой исходных событий (`raw_ads_events`) и ежедневную аналитическую витрину (`campaign_kpi`). Кампания связана с одним каналом; идентификаторы кампаний и каналов сохраняются в каждой записи события, поэтому агрегаты можно строить без неоднозначного восстановления связей.

Сгенерировано 20 000 событий за последние 30 календарных дней. Используются три обязательных типа: `impression`, `click`, `conversion`; присутствуют разные устройства и страны. Данные создаются SQL-генерацией, что обеспечивает воспроизводимость без внешних файлов.

## 2. Движки и типы данных

Для таблиц выбран `MergeTree`: он подходит для аналитических нагрузок, поддерживает сортировочный ключ, партиционирование и TTL. Для справочников использован простой `MergeTree` без партиционирования, так как объём справочных данных мал.

Идентификаторы имеют тип `UInt32`, даты — `Date`, денежные значения — `Decimal`, счётчики — `UInt64`. `event_type` задан как `Enum8`, а `device` и `country` — как `LowCardinality(String)`, поскольку значения этих атрибутов повторяются и принадлежат небольшому множеству.

## 3. ORDER BY и партиционирование

Сырые события сортируются по `(campaign_id, event_date, channel_id, event_type, event_id)`. KPI-витрина сортируется по `(campaign_id, event_date, channel_id)`. Такой порядок соответствует частому аналитическому сценарию: выбор кампании за диапазон дат и последующая агрегация по каналу.

События и KPI-витрина партиционируются по `toYYYYMM(event_date)`. Месячный уровень позволяет работать с историческими диапазонами и управлять хранением, не создавая отдельную партицию на каждый день. Справочники не партиционируются.

## 4. ETL и определения KPI

ETL группирует исходные события по `campaign_id`, `event_date`, `channel_id`. Показы, клики и конверсии считаются через условные агрегаты. Расходы и доходы рассчитываются как суммы полей `cost` и `revenue`.

Используются формулы:

- CTR = clicks / impressions;
- CVR = conversions / clicks;
- CPA = spend / conversions;
- ROI = (revenue - spend) / spend.

CTR, CVR и ROI хранятся как доли, а не проценты. При нулевом знаменателе результат равен нулю. В сравнительных отчётах CPA и ROI рассчитываются на основе суммарных значений за выбранный период, то есть не являются простым средним дневных коэффициентов.

В учебной генерации расход присутствует у каждого события, а доход — у событий конверсии. Такая модель выбрана для прозрачной сверки сумм между сырым слоем и витриной.

## 5. Историчность и TTL

Для `raw_ads_events` задан TTL 24 месяца, для `campaign_kpi` — 36 месяцев. Более длительное хранение агрегированной витрины позволяет сохранять аналитическую историю после истечения срока хранения детальных событий. TTL применяется фоновыми процессами ClickHouse и не гарантирует удаление ровно в момент истечения срока.

## 6. Проверка и оптимизация

Скрипт проверки подтверждает наличие справочников и событий требуемого объёма, наличие всех типов событий и разнообразия устройств/стран. Отдельно проверяется равенство агрегированных показов, кликов, конверсий, расходов и доходов исходным данным.

Скрипт аудита использует `system.parts` для оценки активных частей и партиций, `system.merges` для просмотра фоновых слияний, `system.query_log` для анализа выполненных запросов и `EXPLAIN indexes = 1` для проверки чтения типовой выборки по кампании и дате.

Материализованное представление не применяется: KPI-витрина наполняется отдельным ETL-скриптом. Это упрощает воспроизводимый полный запуск и явную проверку соответствия исходных событий агрегатам.
